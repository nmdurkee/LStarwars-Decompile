1. Executable identity and analysis provenance
OBSERVED: The supplied executable is PE32 x86, native code; its CLR directory is absent. Imports include Direct3D 9, DirectInput 8, XInput1_3 and Bink32. 2. Script command associations and camera path
OBSERVED: Data at 0x007f7618 contains the adjacent values {0x00756354, 0x004509d0, 1}; the first points to "CameraCut". Function 0x004509d0 parses the same camera parameters found in shipped SCP scripts.
INFERENCE, strong: 0x004509d0 is the CameraCut command handler. The data association and matching parameters support this; runtime dispatch was not traced.

Observed flow:
 shipped CameraCut parameters
   -> 0x004509d0: parse parameters, resolve target/locator/object, construct camera settings
   -> 0x00577880: write camera descriptor and position/target state
   -> 0x00577790: write timing/blend state and reset tracking fields

The parser recognizes Reset, use_current_campos, start_time=, end_time=infinite, end_time=, blend_in_time=, blend_out_time=, tgt_locator=, tgt_character=, tgt_obj=, cam_locator=, range=, roty=, rotx=, FollowTgt, dcampos_x/y/z=, campos_x/y/z=, tgtpos_x/y/z= and no_borders.
0x00577880 writes a descriptor at 0x009514f0, a position triple at 0x009518fc/0x00951900/0x00951904 and a target triple at 0x00951908/0x0095190c/0x00951910. Optional target-tracking pointer fields appear at 0x00951920/0x00951924. Their full structures and lifetime are unresolved.

3. Controller hardware polling and internal layout
OBSERVED: XInput1_3 import ordinals are resolved by Ghidra as GetCapabilities (4), GetState (2) and SetState (3). The GetState thunk is 0x00740a64; a call at 0x006d7584 belongs to 0x006d74e0. The function uses pad indices 0–3 when the device-kind field equals 6, calls XInputGetState, and lazily queries capabilities. It also contains a DirectInput branch.

In the XInput branch, the output staging buffer has these byte offsets:
 Offset       Physical input          Stored representation
 0x40–0x43   A, B, X, Y              one byte per button, 0 or 1
 0x44–0x45   left/right shoulder     one byte per button, 0 or 1
 0x46–0x47   Back, Start             one byte per button, 0 or 1
 0x48–0x49   left/right stick click  one byte per button, 0 or 1
 0xc0–0xc3   up, right, down, left   one byte per direction, 0 or 1
 0x00        left stick X            signed 16-bit
 0x02        left stick Y            signed 16-bit, inverted
 0x06        right stick X           signed 16-bit
 0x08        right stick Y           signed 16-bit, inverted
 0x0c–0x0e   left/right trigger      16-bit values, incoming byte shifted left 7
The trigger fields are at 0x0c and 0x0e, not every byte in that range.
The Y paths change -32768 to -32767 before negation. Each stick pair then passes through 0x006d4880.
Button naming uses the official XINPUT_GAMEPAD bit-mask specification:
https://learn.microsoft.com/en-us/windows/win32/api/xinput/ns-xinput-xinput_gamepad

4. Hardware-to-gameplay input mapping — partially traced
Observed call relationships:
 0x006dae50 -> 0x006daa40 -> 0x006d74e0 (poll)
                           -> 0x006d7d80 (mapping)
 0x006d8760 -> 0x006d74e0 (other consumer)

0x006daa40 polls and invokes the mapping routine, returning input values/flags through output parameters. 0x006d7d80 switches on mapping types, including digital reads from staging-buffer + 0x40 + index and positive/negative analog-axis cases. Fields at object + 0x6568 and + 0x67e4 participate in threshold/configuration handling; complete object layouts are not recovered.
0x006d8760 iterates device slots and updates state. Its role beyond that observation is not yet proven.

5. Coverage and interpretation limits
The unpacked-byte scan produced 1,057 candidate name/function records; 227 addresses matched recognized procedure entries and 830 did not. These are candidates, not 1,057 confirmed commands. See dispatch-correlated.json and unpacked-pe/dispatch-candidates.json. The older dispatch-candidates.json at the reports root used the packed input; prefer the unpacked results.
A ResetGameCamera candidate at 0x0044d300 could not be decompiled because this session had no recognized procedure there (rea/003-reset-camera.result.json). Empty Ghidra xrefs for CameraCut do not prove it is unused; the raw data association exists.
Ghidra inferred inconsistent return types between some callers/callees, including the polling wrapper. Missing types, x87 handling and calling conventions require assembly review before treating pseudocode as executable logic.
All decompiled/*.c files are analysis pseudocode with synthetic names, not original source code or a buildable C/C++ project. No patches to the supplied executable were made; only the separate unpacked analysis copy was analyzed.
The static findings have not been checked against a running game. Rendering, physics, collision, navigation, AI scheduling, saves, audio dispatch and the bulk of gameplay code remain outside the completed native scope.
The REA bundle's "unknowns" counter is a tool-record field, not a statement that this investigation has no unknowns. Use the explicit UNRESOLVED items in these reports.
